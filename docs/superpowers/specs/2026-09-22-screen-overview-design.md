# Shared Home Assistant screen overview

The user requests a permanently visible shared Home Assistant selector, simultaneous screen editors beside one another, and automatic option discovery after entering the entity ID. Continue the existing unmerged PR #3 in its worktree, preserving all saved screens and mappings. The user has explicitly authorized this correction and the ongoing build/OTA workflow.

A non-collapsible shared section at the top of Screen contains the single source entity, loading/error/retry status, wake preference and save. Below it, Home and every registered screen appear in a responsive horizontal gallery with their preview/editor, name controls and mapping selectors. Desktop shows at least two screen configurations simultaneously when available; narrow screens scroll horizontally or wrap without hiding controls. + appends and opens a new independent screen. Editing any card must resolve the correct screen context; no data copying between screen slots. Existing ordinary Subpage behavior and explicit card-save flow remain.

Option discovery uses the panel's existing authenticated ESPHome/Home Assistant connection. GET /api/v1/screen-navigation/options?entity_id=<encoded-id> returns {entity_id:string,status:"loading"|"ready"|"unavailable"|"unsupported"|"error",options:string[]}. It reads metadata only, never saves the source or triggers navigation. HTTP queues a bounded lookup; HA operations execute on the firmware main loop. Read only the options attribute of any syntactically valid entity, including custom domains; do not rewrite or restrict user IDs. Standard input_select/select helpers provide lists; missing metadata is reported as unavailable. Invalid IDs return 400; exhausted lifetime discovery capacity returns 429. Existing server authentication applies. Native subscription channels are append-only, so permit at most 16 distinct queried IDs per boot; repeats reuse one channel. Bound raw options to 8192 bytes, 64 options, each at most 255 UTF-8 bytes. Reject oversized/malformed lists rather than truncate values. Decoded cached values share a 16 KiB budget; discovery must not retain raw payloads in the shared HA coordinator. Preserve exact option strings, quotes, commas and whitespace; HA may serialize JSON or a Python-style quoted list. Never interpret code.

Frontend debounces ID edits and polls loading responses with a finite timeout, rejects stale responses from prior IDs, retries explicitly, and preserves mappings/drafts while loading or when unavailable. Each screen chooses one or more exact values from discovered options. Existing values removed from HA remain visibly marked as unavailable and can be removed/replaced; no automatic reassignment. Preserve shared source/wake drafts across editor changes, locales and loading races. Unavailable screen targets remain repairable. The navigation wire format and backups remain compatible.

Verification covers isolated backend lifecycle/parser/endpoint tests, frontend production-path browser tests with multiple visible screens, correct per-screen editing/mapping, persistent global controls, automatic discovery and stale/offline cases, existing regression suites, target build and OTA with the provisioned factory overlay. No fabricated HA options. Actual HA entity confirmation depends on the user's supplied ID and existing connection.


Confirmed behavior: an HA-selected screen remains selected until the next matching entity change. Automatic home timeout and screensaver entry must not discard that selected screen; the screensaver itself still works. Manual navigation away is allowed and resumes ordinary timeout behavior. A state change wakes the panel by default. The source ID is always entered by the user in WWW, never hardcoded. Live-device verification uses the user-confirmed entity already stored in device settings.

Default long press opens a controls/details menu (for a light, brightness/color controls), never the ordinary tap action. Releasing after a recognized hold must not execute a click. Preserve explicit custom more_info and none choices. Menu-only card types reuse safe dedicated modal openers; action-only/read-only cards fall back to details without running actions. Ordinary lights need an owned temporary control context without overwriting their existing visual/userdata ownership. Keep wake-only and child-slider guards, and release subscriptions when temporary menus close or the grid rebuilds.
